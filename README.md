# 灯杆故障单入仓核对系统（Flask + SQLite）

巡检台账与维修台账把**两根灯杆误认成同一根**时，故障单会挂到多个资产号上。
本系统用网页完成入仓核对：上传资产号清单、故障单与同杆确认，按同杆关系把灯杆并成
冲突组，给出“撤销一条同杆确认即可让组内每张单都有唯一资产号”的方案；选定后按
**最新资料复算**，条件满足才撤销并生成整组入仓清单。

## 一、启动（Docker Compose）

```bash
docker compose up --build
# 浏览器打开 http://localhost:8000
```

SQLite 数据文件落在宿主机 `./data/recon.db`（compose 已挂载卷），重建容器不丢数据。
停止：`docker compose down`。

## 二、CSV 格式（均为 UTF-8，首行表头）

| 上传类型 | 列 | 说明 |
|---|---|---|
| 资产号清单 | `asset_no,pole_source,pole_no` | 资产号全局唯一；后两列是该资产所在灯杆的来源台账与灯杆号。**全量替换**（已有单子核对到资产时拒绝替换） |
| 故障单 | `ticket_no,source,pole_source,pole_no` | 单号按来源台账区分；可补传，同 `(source,ticket_no)` 为更新 |
| 同杆确认 | `source_a,pole_no_a,source_b,pole_no_b[,confirmed_by]` | 被认成同一根的两根灯杆引用；可补传，幂等；撤销后同对灯杆可再次确认 |

样例见 `sample_data/`。编号在页面统一显示为 `来源/编号`，从根上区分不同台账的同号灯杆/单号。

## 三、核对与撤销规则（实现要点）

1. **按来源区分编号**：灯杆、故障单都以 `(来源, 台账内编号)` 为自然主键，不同台账同号互不覆盖。
2. **同杆确认可传递**：活动确认构成无向图，并查集求连通组；一张确认撤销后只影响它所在的组。
3. **冲突组**：含 ≥2 个灯杆引用且有故障单的连通组。组内资产号候选池为各灯杆上资产号的并集，
   每张故障单必须匹配不同资产号（二分图 Kuhn 匹配，确定性结果）。
4. **单条撤销方案**：逐条模拟“移除该确认”，当且仅当拆出的每个子组都能一一匹配时列为方案，
   页面同时给出撤销后每张单的归属资产号；没有任何确认可满足时提示**无解**。
5. **选定方案后按最新资料复算**（不依赖选方案时的快照）：
   - 重新定位组、确认该确认仍活动且仍在组内（资料已变则要求**重新选择**）；
   - 模拟撤销重新匹配；
   - **已核对单子归属不变**、且最新组里的新单也都有唯一归属，两个条件同时满足才执行；
   - 撤销确认、锁定归属、生成整组入仓清单在**单个 SQLite 事务**内完成；
   - 条件不符或写入失败一律回滚，保留原关系和归属并提示原因。
6. 已核对单在后续匹配中作为强制边：原归属资产不在组内或被迫改变时，方案直接判失败。

## 四、页面

- `/` 上传三种 CSV；展示数据统计、冲突组（当前是否可唯一归属、已选方案、入仓链接）、上传批次。
- `/groups/<key>` 组详情：故障单/候选资产/已核对锁定单；列出全部单条撤销方案及撤销后归属；无解提示。
- `/warehouse/<id>` 整组入仓清单：每张单的唯一资产号，标注“已核对（归属保持不变）/本次新核对”。

## 五、验证

自动化测试（9 个用例，Flask test client + 临时 SQLite）：

```bash
python tests/test_recon.py
```

覆盖：三类上传与补传/幂等、来源编号区分、传递分组、方案选择与撤销入仓、
**补传后仍可撤销（已核对单归属不变）**、**补传后无解与须重选**、坏 CSV 整体拒收、
写入失败事务回滚保留原关系。

另做过真实 HTTP 冒烟（上传 → 选方案 → 复算撤销 → 补传无解 → 补传后重选成功），
结果与测试一致。

## 六、目录结构

```
app/
  db.py          SQLite 连接与建表（POLE_RECON_DB 可覆盖库路径）
  services.py    CSV 入仓、并查集分组、Kuhn 匹配、撤销方案与复算入仓
  routes.py      Flask 路由
  templates/     网页模板
tests/test_recon.py
sample_data/     三份示例 CSV
Dockerfile / docker-compose.yml / entrypoint.sh
```

## 七、余项与边界

- 资产清单按“全量替换”设计；若已产生核对关系，上传会被拒绝并提示，避免静默读旧归属。
- 单机部署、SQLite 单文件；如需多实例，可换 PostgreSQL（DAO 集中在 `db.py`/`services.py`）。
- 未做登录鉴权，内网工具定位；上生产前需加认证并替换 `app.secret_key`。
- 冲突组只展示由同杆确认合并出来的多灯杆组；单灯杆自身“单多于资产”的资料问题不在本流程处理范围。
